# SEC 公共请求入口与跨进程限流 — 已审核，已实现待部署

> 日期：2026-10-20。
> 用户已审核并允许实施；本轮仅实施本方案，生产迁移和采集恢复仍另行确认。
> 本步只修复一个问题：本机各 SEC 采集入口分别限流，无法保证合计不超过 2 次/秒。

## 1. 目标与边界

本机财务同步、行业分类、原文核查及回补脚本的 SEC 请求统一经过公共客户端。初期全局串行执行，每次请求结束后至少间隔 0.5 秒，再开始下一次请求；实际吞吐可以低于 2 次/秒。

- 本次读取当前配置确认 `STOCK_MARKETS=US`，财务客户端加载的 `rate_limit=10`。项目规则要求的 2 次/秒尚未落实到这些入口。
- 审核补充：本机 `.env` 没有显式 `STOCK_SEC_RATE_LIMIT`，当前 10 来自代码默认值；并非遗留环境覆盖。
- 本步交付公共客户端、PostgreSQL 协调状态及现有入口接入，不实现公告采集、资讯表、UI 或公告调度。
- 公告检查间隔独立于请求速率；此前建议的每 60 分钟检查一次，不在本步修改或启用。
- 只协调本机、连接同一 PostgreSQL 数据库的项目任务。大陆机器的 A 股/港股来源、Hyperliquid 和公司 IR 请求不进入此额度。
- 不增加 Redis、消息队列、独立常驻采集服务或跨库通信。

## 2. 依据、现状与接入范围

SEC 官方要求每个用户合计不超过 10 次/秒，不因机器数增加额度。本项目选择更保守的 2 次/秒；该数值是上限，不是必须达到的吞吐目标。来源：[SEC Developer Resources](https://www.sec.gov/about/developer-resources)。

继续使用已有 SEC 来源，不引入新的数据提供方：`companyfacts` 提供结构化财务事实，`submissions` 提供申报与公司元数据，Archives 提供原始文件。参见 [SEC API 说明](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)。本步不改变财务字段映射、来源优先级、证券身份或快照语义。

## 3. 公共客户端与配置

拟新增 `core/sec_client.py`，提供只读 GET 能力。输入为受控 SEC URL、调用任务名称、可选证券/CIK 与请求预算；输出保留状态码、响应头、字节正文和最终 URL，供现有解析器继续使用。

- 统一使用 `config.sec.user_agent`；请求日志带任务、证券/CIK、尝试次数、等待时长、状态及错误类型，不记录凭据或整段正文。
- `STOCK_SEC_RATE_LIMIT` 默认改为 `2`，本步只允许正整数 `1` 或 `2`。旧环境若显式配置 `10`，应在联网前明确报配置错误，不能悄悄保留或忽略。
- 全局最短间隔为 0.5 秒；配置 1 次/秒的调用者采用更长间隔，不能缩短共享暂停时间。
- 禁用 HTTP 库隐藏重试和自动重定向。每次重试、每个重定向跳转均重新经过协调入口；仅允许 HTTPS 的 `www.sec.gov` / `data.sec.gov`，重定向最多 3 跳，其他目标明确报错。
- HTTP 重试只由公共客户端负责。移除接入路径中重复的 HTTP 重试循环；外层业务重跑仍须经过客户端，不能吞掉协调错误后继续直连。
- 缓存命中或纯本地解析不需要获取额度，也不因为引入客户端而额外联网。

## 4. PostgreSQL 跨进程协调

使用固定命名空间的 PostgreSQL **会话级 advisory lock**，配合一行持久状态。所有入口使用同一个协调 key，不能按 endpoint、任务或 PID 各建一份额度。

拟新增独立迁移 `scripts/sec_request_gate.sql` 与表 `sec_request_gate`：

| 字段 | 含义 |
|---|---|
| `gate_key` | 主键，固定为项目 SEC 出站额度标识 |
| `next_allowed_at` | 正常间隔或异常退出保护结束时间，`timestamptz` |
| `blocked_until` | SEC 限流响应或退避要求产生的共享暂停时间，`timestamptz` |
| `updated_at` | 最后一次状态更新的数据库时间 |

初始化行由迁移创建。缺表、缺行、连接错误或状态非法均阻止联网，并提供迁移/配置错误；不自动退回进程内限流。迁移只新增对象，不写已有财务表。实施时同步 `docs/core/SCHEMA.md` 与 `docs/core/ARCHITECTURE.md`。

### 一次物理 HTTP 请求的顺序

1. 使用专用数据库连接尝试获取会话锁。连接不使用业务事务连接，也不把仍持锁的连接归还普通池；连接数量按进程约束，进程内再用互斥控制。
2. 在锁内读取共享状态，以数据库时间判断是否可执行。尚在暂停期则释放锁后等待，再重新竞争和读取；不缓存一个过期的“通行许可”。
3. 请求发出前，提交一段异常退出保护时间：至少覆盖本次 HTTP 的总时限及最短间隔。随后保持会话锁，执行一次有界 HTTP 请求。网络期间没有未提交的长事务。
4. 正常结束后，在仍持锁时把 `next_allowed_at` 更新为数据库当前时间加最短间隔；失败结束也计入间隔。若需要共享退避，同时延长 `blocked_until`，不能覆盖成更早时间。
5. 提交状态后才释放锁、关闭响应与连接；重试或跳转返回第 1 步。状态写入失败时保留预先提交的保护时间并抛协调错误，不能返回成功后继续发请求。

正常情况下保证全局同时只有一个请求在执行。相较于每秒集中放行两个请求，这种方式更保守，也会拉长批量财务任务耗时。

这是有意取舍，不提供突发额度。若每次请求平均耗时为 L 秒，忽略其他开销时吞吐约为 `1 / (L + 0.5)` 次/秒。1000 家公司的请求数取决于缓存、增量筛选和原文补缺；Company Facts 通常每家公司一次，不能固定按每家 2～3 次推导。30～50 分钟仅作为批量回补的情景估算，不是耗时承诺；实施验证记录实际吞吐与外层超时约束。

### 进程退出与连接失效

- 正常异常路径使用 `finally` 释放锁和连接；进程被终止后，由 PostgreSQL 在会话终止时释放锁。连接断开被数据库识别前，其他任务可能等待并超时，不能擅自绕过锁。
- 持久的异常退出保护防止进程被杀后立即连续补发请求；新进程不得清空这段等待时间。进程退出与重启纳入验收。
- 协调连接失效后，原持有者不得自动重连并沿用旧许可。放行前再次确认协调连接与剩余请求时限；发现失效应停止后续发送/重试。
- 本机数据库锁不是跨机器出站代理。数据库重启或网络分区期间，不承诺能撤销已经送出的 HTTP；应使任务明确失败、停止继续发送，并在恢复时保留有效保护窗口。若做不到有界 HTTP 与失效处理，不得声称异常情况下仍能保证全局串行。

## 5. 超时、重试与错误语义

初始预算建议固定为：单次 HTTP 连接超时 5 秒、读取空闲超时 30 秒、单次 HTTP 总时限 60 秒；一次逻辑 GET（含等待、重试和跳转）总时限 180 秒。请求剩余预算不足时不得再发出；排队等待超时和 HTTP 超时分开记录。

`requests` 的连接/读取 timeout 不等于完整下载总时限。实现必须真正约束总耗时并终止底层请求，不能只让等待线程超时、留下后台 HTTP 继续运行；须用慢速响应测试验证。

- 可重试的网络故障、429、500/502/503/504：最多重试 2 次（首次加重试共 3 次尝试），共享退避初值 2 秒、随后 4 秒。每次发送继续计入全局额度。
- 429 及带有效 `Retry-After` 的 503：解析秒数和 HTTP 日期，暂停时间取服务器要求与本地退避的较大值；缺失/非法值明确记录并采用保守退避（429 至少 10 秒）。
- 服务器要求的暂停超过当前调用剩余预算时，持久保留完整暂停时间，并返回包含可重试时间的明确错误；不能截短后提前请求。
- 403 不紧密重试；记录共享暂停 60 秒并返回明确访问错误，不将其一律诊断为速率超限。其他不可重试的 4xx 返回明确错误。
- 协调失败、等待超时、HTTP 失败不得被接入方转换成“没有公告”“财务为空”或成功。现有业务允许的 404/缺字段状态可以保留，但必须与协调故障区分；缓存降级如已存在，也必须显式标明。
- 重试等待期间释放会话锁；其他任务仍须遵守共享暂停。不新增任务优先级或严格 FIFO 保证，等待超时必须可见。

## 6. 与现有功能的冲突和上线边界

| 影响 | 处理 |
|---|---|
| 批量财务任务变慢 | 接受实际吞吐低于 2 次/秒；验证外层任务超时是否仍合理，不以恢复独立限流解决 |
| 原来无需数据库的网络脚本增加依赖 | 网络下载必须连接同一个协调库；纯离线分析不强制连接数据库。迁移前这些网络路径明确不可用 |
| 宽泛异常捕获可能吞掉新错误 | 检查上述接入点，把协调错误传播为任务失败或明确部分失败，不能伪装成无记录 |
| 新旧版本进程同时运行 | 旧进程不会遵守新协议，上线前必须暂停新任务并等待/停止旧 SEC 作业；换版本后统一重启相关进程 |
| 回退到旧代码后失去共享限制 | 回退期间保持 SEC 自动任务停止，不边回退边恢复旧直连任务；新增表可保留，不删除业务数据 |
| 协调范围有限 | 只有使用同一数据库/key 的客户端受控；本步不把本机限流宣称为跨机器或仓库外请求的总限流 |

实施交付提供代码、迁移和检查记录。生产迁移、停止/重启任务和恢复采集在交付审核后另行执行；本次方案编写不触发这些操作。

## 7. 验收标准

1. **真实跨进程协调**：在隔离测试数据库中启动多个独立进程，使用受控 HTTP 测试端，记录实际发送时点与并发数；正常情况下最大并发为 1，相邻请求之间满足结束后至少 0.5 秒的间隔，任意半开 1 秒窗口内最多 2 次请求。不能只用单进程 mock 证明共享限流。
2. **绕过检查**：逐一验证第 2 节入口，首请求、重试、重定向都经过公共客户端；特别检查行业、股本回补的 UA 统一，以及 scheduler/财务回补循环创建多个 fetcher 的路径。无库内请求包装遗漏，无旧 HTTP 重试在后台额外发包。不存在源码直连遗漏才可宣称接入完成。
3. **共享退避**：进程 A 收到 429/Retry-After 后，进程 B 在共享暂停到期前不能发包；长暂停、HTTP 日期和非法头分别覆盖。
4. **故障恢复**：覆盖缺迁移、数据库不可用、锁等待超时、持锁进程被杀、重启、协调连接中断、状态更新失败；不绕过协调、不永久遗留锁、不伪装成功。保护窗口仍生效。
5. **有界传输**：慢响应/持续少量数据的响应仍能在总时限内终止，不遗留后台请求；HTTP 自动重试与自动跳转确已关闭。
6. **调用方回归**：财务缓存与版本化、SIC 解析、原文补缺、核查和回补的既有字段/结果保持一致；协调错误能到达调用方。离线缓存路径不新增 SEC 请求或数据库依赖。
7. **配置与隔离**：默认值为 2，显式 10/非法配置在联网前失败；CN_A/CN_HK 的请求和 Hyperliquid 不受 SEC gate 控制。

测试使用离线 fixtures、受控传输与隔离 PostgreSQL，不以生产 SEC 压测作为验收。真实 SEC 连通性验证如需执行，只做少量请求并经过同一客户端。
