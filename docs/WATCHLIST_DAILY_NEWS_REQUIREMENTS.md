# 关注公司与直接相关行业的每日资讯 — 需求与来源验证（待审核）

> 日期：2026-10-20。
> 本文记录已讨论的产品需求，并提出当前一步的来源验证范围，供用户审核。
> 本步只解决“哪些来源能支持每日阅读，以及覆盖缺口是什么”，不启动生产采集、数据库迁移、界面开发或部署。

## 1. 目标与已确认范围

用户作为 trader，需要每天阅读关注公司及其直接相关行业的新消息。官方公告、公司新闻和相关行业新闻都是核心需求；SEC 接通只能代表一种来源接通，不能代表每日资讯能力交付。

每日使用应能回答：

1. 从上次阅读到现在，关注公司和相关行业发生了什么？
2. 哪些消息直接涉及公司，哪些通过竞争、供需或产业链关系影响研究？
3. 消息来自哪里、何时发布、有哪些后续进展，如何查看原始材料？
4. 当前没有新消息，还是来源未接入、采集失败或更新滞后？

部署边界沿用用户确认：美股和 Hyperliquid 在本机，A 股和港股在大陆机器。2026-10-20 本机 `.env` 的 `STOCK_MARKETS=US`；本次来源验证仅覆盖美股。股票与 Hyperliquid 的来源、业务分类和调度分别定义，本文不安排其他市场或 Hyperliquid 的实施任务。

## 2. 产品参照及取舍

## 3. 阅读体验与内容边界

### 3.1 每日入口

建议以跨关注公司的资讯列表作为每日阅读入口，支持今日、隔夜、未读/上次阅读后新增，并可按公司、行业主题和来源类型筛选。公司详情页展示该公司的相关资讯，两处使用一致的来源和时间口径。

“今日”应基于明确显示的阅读时区；不能默默混用北京时间和美东交易日。“未读”是阅读状态，“新增”是系统发现状态，两者不能混为一谈。历史回补条目应标明回补，避免被误认为刚发生的事件。2026-10-20 用户确认：日期划分以北京时间为准，每条资讯同时明确标注时区（原始时区与北京时间对照）。

### 3.2 内容范围

| 类型 | 覆盖内容 | 必须保留的区别 |
|---|---|---|
| 官方披露 | SEC 申报、修订及相关原文入口 | 表单描述与新闻标题不同；SEC 接收时间不等于事件首次公开时间 |
| 公司发布 | IR 新闻、业绩与指引、产品、合同及经营动态等 | 公司自身陈述与外部独立报道不同 |
| 公司新闻 | 外部媒体对公司的报道，包括分析师观点、竞争和监管等事件 | 事实报道、评论、传闻及其原始出处分别标注 |
| 直接相关行业 | 产品供需与价格、竞争对手、主要上下游、直接影响业务的政策等 | 说明与关注公司的关联依据，不能仅因同属一个宽泛行业就全部纳入 |

例如，对 MU 的主题配置可考虑存储、DRAM/NAND/HBM、供需价格、竞争产能和下游需求。该例是覆盖设计示例，不代表这些来源已验证。直接相关的新闻即使没有出现股票代码，也应有机会进入阅读范围。

关联理由先用可核对的公司—业务主题—上下游/竞争关系配置表达。关系需有依据；“与公司相关”不自动表示“利好/利空”或“已影响盈利”。

### 3.3 每条资讯的最低阅读信息

- 原标题、涉及公司或主题、关联理由、来源名称和原文链接。
- 来源类型，以及报道、评论、传闻等内容性质；采集成功不能被标为事实已核实。
- 原始发布时间与精度、系统首次发现时间；缺失或仅有日期时明确标示。
- 同一事件的重复转载可以折叠，保留来源入口；后续更新、修订和不同观点不能被误删。
- 来源上次成功检查时间、覆盖范围和异常状态；不能用最后一条新闻的发布时间代替采集健康状态。

这些是后续产品合同的输入，本步不确定表结构、API 路径或事件聚类算法。AI 摘要可后续讨论；原始标题、来源和时间不能依赖 AI 生成才能使用。

## 4. 当前一步：验证来源是否足够支持每日阅读

### 4.1 样本与窗口

建议从实际美股关注名单中选取三家公司，尽量覆盖至少两类业务主题。MU、WDC、NBIS 可作为候选，执行时须先核对是否仍在关注名单及其当前业务关联，不能把旧名单当成已确认事实。

以验证执行日前最近 7 个完整自然日为固定窗口，记录起止时间和时区。若某类事件没有样本，可补充最近 30 日的实例，但需单独标记，不能混入 7 日统计。样本不足时报告证据不足，不推断来源具有完整覆盖。

### 4.2 候选来源

在同一窗口对照官方披露/公司发布、综合公司新闻、行业专业来源。优先验证具有明确 API、RSS 或稳定官方入口的来源，记录实际访问方式；搜索可帮助建立参考样本，不能将搜索摘要冒充已接入的持续新闻源。2026-10-20 用户确认：初期接受"非官方但稳定"的来源（如 Google News RSS）作为主召回源，初步候选组合为 Google News RSS + Finnhub 免费档 + TrendForce/Blocks & Files 等行业站；更具体的来源质量标准待上线体验后提出，本步验证不以"全部官方接口"为通过条件。

每个候选来源填写：

| 维度 | 要记录的证据 |
|---|---|
| 接入方式 | 官方入口或文档、API/RSS/网页方式、认证需求、分页与历史范围 |
| 覆盖 | 实际命中的公司、行业主题、内容类型，以及明确漏掉的参考事件 |
| 内容 | 可取得标题、链接、时间、摘要还是正文；是否有稳定 ID 和修订信息 |
| 关联 | 代码直连、公司别名或主题关系命中；保留关联理由及误匹配实例 |
| 时间 | 来源发布时间、首次观察时间、时间精度；历史样本不能证明实时到达延迟 |
| 成本与使用条件 | 当前可验证的额度、频率限制、费用及允许的展示/保存方式；未知项明确列出 |
| 可用性 | 本机访问结果、失败表现、动态加载或历史不可访问等限制 |

建立一份带原文链接的人工参考事件清单，分别包含公司公告、公司新闻、直接行业新闻。对照候选源，报告“参考样本中命中 N/M”、无关条目比例、重复情况和具体遗漏；该清单不是全网真值，不能宣称全网召回率。

历史覆盖与更新时效分别评价。本步可以形成历史覆盖结论；若没有前瞻观察证据，实时延迟列为未验证，不用旧文章时间反推采集速度。

### 4.3 时间与限流约束

- 项目 SEC 请求上限维持 2 次/秒；此额度只约束 SEC，不套用到新闻、IR 或 Hyperliquid。
- 用户已要求降低初期 SEC 检查频率。[公告子阶段方案](WATCHLIST_ANNOUNCEMENTS_MVP_PLAN.md) 已修订为 SEC/IR 默认每 60 分钟的可配置提案，替代旧的 5/15 分钟值；该提案仍待审核，尚未启用。
- 新闻刷新频率依据来源更新能力、额度和盘前/盘中使用要求确定，不直接复制 SEC 间隔。
- “每日阅读”不等于“一天采集一次”；具体延迟目标尚未确认，本步不承诺实时新闻服务。

### 4.4 本步交付与审核门槛

交付一份来源验证记录，包含样本公司与主题、时间窗口、参考事件清单、候选源证据、覆盖对照和缺口。结论需明确：

1. 是否存在可用的来源组合，同时覆盖官方信息、公司新闻和直接行业新闻。
2. 哪些能力已实测，哪些仅有官方说明，哪些需要账号、付费或更长观察。
3. 每个遗漏是来源没有、关联规则没有命中，还是访问/历史范围限制。
4. 推荐组合及取舍；若证据不足，说明缺少什么，不以空列表或“暂无新闻”掩盖问题。

本步完成标准是形成可复核的选源依据；是否接受覆盖、成本与延迟取舍，由用户审核。来源验证结束不等于生产信息流已可用。
