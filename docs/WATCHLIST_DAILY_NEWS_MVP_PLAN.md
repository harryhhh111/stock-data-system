# 每日资讯 MVP（公司新闻层）— 待审核

> 日期：2026-10-22。本方案是 [每日资讯需求](WATCHLIST_DAILY_NEWS_REQUIREMENTS.md) 的第一实施片，只覆盖**公司新闻层**（外部媒体对关注公司的报道）。
> 依据：[线 A 来源验证终审归档](WATCHLIST_DAILY_NEWS_SOURCE_VALIDATION.md)——Google News RSS 主召回（基准 15/15）+ Finnhub 提供证券标签、稳定 ID、交叉核对（11/15）。
> 官方披露层（SEC/IR）已完成并上线，本片将其数据接入同一信息流展示，不改其采集逻辑。
> 2026-10-22 用户已确认：独立每日资讯页（置顶 + 时间流，版式密度参考 aihot.news，不做金十式高密度快讯）；**产品设计一体化考虑公司+行业两层（schema/API/页面的来源类型、关联理由、折叠机制不得把行业层挡在门外），但实施分期——本片只做公司层**，行业主题层下一期接入；复用公告表并加列迁移；每日落库、采集间隔初始 6 小时、要过滤规则、要折叠去重；初版不做已读状态。置顶规则确认：近 24h 官方披露 + 折叠后来源数 ≥2 的媒体组。

## 1. 目标与边界

用户每天打开一个页面，回答「从昨天到现在，我关注的公司发生了什么」。

- 覆盖：关注名单 6 家 US 公司的媒体报道 + 已采集的官方披露（同页统一阅读，来源类型严格区分）
- 不做：行业主题新闻（下一期）、已读/未读状态、AI 摘要/打分/翻译、正文抓取、推送通知、港股/A 股/Hyperliquid
- 时间口径沿用已确认规则：日期划分以北京时间为准，每条标注原始时区与北京时间；「未读」不实现，初版按时间窗口浏览

## 2. 采集（每日落库是硬需求）

线 A 实测约束：Google RSS 单查询 100 条硬上限、无分页、热查询回溯约 7~10 天 → 必须按固定间隔持久化，事后补不回来。

- **来源注册**：复用 `watchlist_announcement_source`，新增 `source_kind='media'`。每股两个媒体来源：`google_news_rss`（按公司查询词）与 `finnhub`（按 symbol）。注册表加查询配置（公司名/别名查询词），新增公司 = 加注册行
- **查询构造**：
  - Google News RSS：线 A 验证过的查询形态（公司名+ticker），固定入口 `news.google.com/rss/search`，解析 pubDate/guid/link
  - Finnhub `/company-news?symbol=X&from=&to=`：from 取当日−1 天（线 A 已指出 from 日期不覆盖北京时间窗口起点的问题，采集侧留冗余）；用返回的稳定 id 去重
- **间隔**：新增 `STOCK_ANNOUNCEMENTS_MEDIA_INTERVAL_MINUTES`，默认 360（6 小时，用户定）；正整数校验、注册前报错，与 SEC/IR 同一整轮 advisory lock 串行执行；媒体源不占 SEC gate，各自保守限速（每源一次请求/轮，无重试循环）
- **去重身份**：RSS 用 guid（回退规范化 link）；Finnhub 用 id；均落 `source_record_id`，复用现有 revision/幂等机制
- **回补标记**：复用 `is_backfill`；首次接入的历史条目标明回补，不冒充新发生

### 2.1 过滤规则（线 A：Finnhub 相关率仅 60~70%）

v1 规则（简单、可解释、可复核）：**标题+摘要不含该公司名称/别名/ticker 任一命中 → 丢弃**，并记录每轮丢弃计数（运行记录可见，不静默）。命中词表来自注册表查询配置。误杀与误放的评估等上线有体验后再细化（用户已确认质量标准后置）。

### 2.2 折叠去重（展示层，不动存储）

- 存储层全量保留各来源各自记录（合同：不同来源报道同一件事保留各自记录）
- 展示层折叠：规范化标题（小写、去标点、去来源后缀如 " - Reuters"）相同且发布时间相差 ≤48 小时的媒体报道折成一组，显示代表条 + 来源数 + 全部来源入口
- 标题不同的不折叠——后续更新、修订和不同观点不得被误删（需求 §3.3）

## 3. schema 迁移（加列，幂等）

`watchlist_announcement` 加两列（合同审核备注预留：内容性质与关联理由留待新闻阶段加列）：

- `content_nature TEXT`：报道/评论/传闻的区分。**v1 媒体条目一律 `'unclassified'`**，UI 显示「内容性质未分类」——v1 没有可靠自动判别手段，不伪造为「报道」；官方披露行不受此列约束
- `relation_reason TEXT`：v1 写机器可核对的理由，如 `ticker 直连：Google 查询词 "Micron"` / `Finnhub symbol MU`

迁移只加列，不动既有行与财务对象；SCHEMA.md 同步。

## 4. API（只读，只查库，不触发外网）

- `GET /watchlist/news/feed?date=YYYY-MM-DD&stock=&kind=all|official|media`：按北京时间自然日的信息流，折叠后返回；每条含标题、来源名、来源类型、内容性质、关联公司、关联理由、发布时间+精度+原始时区、首次发现时间、回补标记、折叠组（来源列表）、原文链接。缺失时间单独标注按发现时间排序
- `GET /watchlist/news/pinned`：置顶区（规则见 §5，待确认）
- 媒体来源状态并入既有五态（复用公告片的来源状态字段与语义）；窗口内无条目时区分「已接入来源暂无资讯」与「来源不可用」

## 5. 前端：每日资讯页 `/news`

形态参考 [aihot.news](https://aihot.news/) 与金十数据首页：**置顶区 + 按北京时间日期分组的时间流**。**不做 AI 评分/精选/推荐理由**（需求 §3.3：原始标题、来源和时间不依赖 AI 生成）。

- 置顶区提案（**待用户确认**）：近 24 小时内的官方披露（SEC/IR）+ 折叠后来源数 ≥2 的媒体报道组
- 时间流：按日期分组（如「10 月 22 日 · N 条」），每条显示原标题（英文原文，不翻译）、来源、北京时间+原始时区、关联公司标签、来源类型徽标（官方披露/媒体）、内容性质标注、折叠来源数、原文外链
- 筛选：按公司、按来源类型（全部/官方/媒体）
- 侧栏加入口；关注股弹窗逻辑不动
- react-query 轮询读库；只渲染安全文本与受校验链接

## 6. 验收

1. 离线 fixture 测试：RSS XML 与 Finnhub JSON 用线 A 归档证据快照（`docs/evidence/watchlist_daily_news/`）转 fixture；覆盖解析、去重幂等、过滤计数、折叠边界（48h、标题差异不折叠）、时区、回补标记
2. **基准回放**：线 A 基准表 v2 的 15 个事件离线重放，Google 源应 15/15、Finnhub 应 11/15；不达标即阻塞本片
3. 迁移幂等 + 缺表降级（同公告片：仅公告 schema 缺失降级，其他 DB 错误 503）
4. API/前端：pytest + tsc + 构建通过；页面 GET 无外网请求；五态与空态语义复验
5. 明确不做真实采集启用——部署（迁移执行 + 媒体源启用 + 首轮回补验证）另行授权

## 7. 明确不做

行业主题新闻与关联配置、已读状态、AI 摘要/翻译/打分、正文抓取与全文存储、推送、多市场、写接口。媒体源历史回补窗口与 partial 语义沿用公告片既有机制。
