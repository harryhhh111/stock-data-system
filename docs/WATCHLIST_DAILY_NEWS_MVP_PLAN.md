## 1. 目标与边界

用户每天打开一个页面，回答「从昨天到现在，我关注的公司发生了什么」。

- 覆盖：关注名单 6 家 US 公司的媒体报道 + 已采集的官方披露（同页统一阅读，来源类型严格区分）
- 不做：行业主题新闻（下一期）、已读/未读状态、AI 摘要/打分/翻译、正文抓取、推送通知、港股/A 股/Hyperliquid
- 时间口径沿用已确认规则：日期划分以北京时间为准，每条标注原始时区与北京时间；「未读」不实现，初版按时间窗口浏览

## 2. 采集（每日落库是硬需求）

线 A 实测约束：Google RSS 单查询 100 条硬上限、无分页、热查询回溯约 7~10 天 → 必须按固定间隔持久化，事后补不回来。

- **来源注册**：复用 `watchlist_announcement_source`，新增 `source_kind='media'`。每股两个媒体来源：`google_news_rss`（按公司查询词）与 `finnhub`（按 symbol）。注册表加查询配置（公司名/别名查询词），新增公司 = 加注册行
- **查询构造**：
  - Google News RSS：线 A 验证过的查询形态（公司名+ticker），固定入口 `news.google.com/rss/search`，解析 pubDate/guid/link
  - Finnhub `/company-news?symbol=X&from=&to=`：from 取当日−1 天（线 A 已指出 from 日期不覆盖北京时间窗口起点的问题，采集侧留冗余）；用返回的稳定 id 去重
- **间隔**：新增 `STOCK_ANNOUNCEMENTS_MEDIA_INTERVAL_MINUTES`，默认 360（6 小时，用户定）；正整数校验、注册前报错，与 SEC/IR 同一整轮 advisory lock 串行执行；媒体源不占 SEC gate，各自保守限速（每源一次请求/轮，无重试循环）
- **去重身份**：RSS 用 guid（回退规范化 link）；Finnhub 用 id；均落 `source_record_id`，复用现有 revision/幂等机制
- **回补标记**：复用 `is_backfill`；首次接入的历史条目标明回补，不冒充新发生

### 2.1 过滤规则（线 A：Finnhub 相关率仅 60~70%）

v1 规则（简单、可解释、可复核）：**标题+摘要不含该公司名称/别名/ticker 任一命中 → 丢弃**，并记录每轮丢弃计数（运行记录可见，不静默）。命中词表来自注册表查询配置。误杀与误放的评估等上线有体验后再细化（用户已确认质量标准后置）。

### 2.2 折叠去重（展示层，不动存储）

- 存储层全量保留各来源各自记录（合同：不同来源报道同一件事保留各自记录）
- 展示层折叠：规范化标题（小写、去标点、去来源后缀如 " - Reuters"）相同且发布时间相差 ≤48 小时的媒体报道折成一组，显示代表条 + 来源数 + 全部来源入口
- 标题不同的不折叠——后续更新、修订和不同观点不得被误删（需求 §3.3）

## 3. schema 迁移（加列，幂等）

`watchlist_announcement` 加两列（合同审核备注预留：内容性质与关联理由留待新闻阶段加列）：

- `content_nature TEXT`：报道/评论/传闻的区分。**v1 媒体条目一律 `'unclassified'`**，UI 显示「内容性质未分类」——v1 没有可靠自动判别手段，不伪造为「报道」；官方披露行不受此列约束
- `relation_reason TEXT`：v1 写机器可核对的理由，如 `ticker 直连：Google 查询词 "Micron"` / `Finnhub symbol MU`

迁移只加列，不动既有行与财务对象；SCHEMA.md 同步。

## 4. API（只读，只查库，不触发外网）

- `GET /watchlist/news/feed?date=YYYY-MM-DD&stock=&kind=all|official|media`：按北京时间自然日的信息流，折叠后返回；每条含标题、来源名、来源类型、内容性质、关联公司、关联理由、发布时间+精度+原始时区、首次发现时间、回补标记、折叠组（来源列表）、原文链接。缺失时间单独标注按发现时间排序
- `GET /watchlist/news/pinned`：置顶区（规则见 §5，待确认）
- 媒体来源状态并入既有五态（复用公告片的来源状态字段与语义）；窗口内无条目时区分「已接入来源暂无资讯」与「来源不可用」

## 5. 前端：每日资讯页 `/news`

形态参考 [aihot.news](https://aihot.news/) 与金十数据首页：**置顶区 + 按北京时间日期分组的时间流**。**不做 AI 评分/精选/推荐理由**（需求 §3.3：原始标题、来源和时间不依赖 AI 生成）。

- 置顶区提案（**待用户确认**）：近 24 小时内的官方披露（SEC/IR）+ 折叠后来源数 ≥2 的媒体报道组
- 时间流：按日期分组（如「10 月 22 日 · N 条」），每条显示原标题（英文原文，不翻译）、来源、北京时间+原始时区、关联公司标签、来源类型徽标（官方披露/媒体）、内容性质标注、折叠来源数、原文外链
- 筛选：按公司、按来源类型（全部/官方/媒体）
- 侧栏加入口；关注股弹窗逻辑不动
- react-query 轮询读库；只渲染安全文本与受校验链接

## 9. 多公司关联展示修订（2026-10-27，已实现待验收）

### 9.1 问题与本片边界

MU、WDC 各收录一条同题报道时，后端 `_media_group_entry` 只保留代表条的公司集合，前端又仅渲染 `entry.stock_code`，导致折叠组的其他关联公司不可见。`feed` 在聚合前按所选公司过滤，还会提前移除其他公司的关联记录。

本片目标：**同题新闻仍只展示一组，但完整保留该组在当前候选范围内关联的关注股；从任一家关联公司的筛选入口都能找到它。**

这是展示聚合和接口契约修复，不新增采集源、不改存储身份或数据库 schema，不补采、不增加 AI 推断，不扩展为事件语义聚类。现有标题规范化、48 小时分组边界、未知时间独立成组、代表条选择、中文增强及置顶评分规则保持原有口径。R1 证券目录补齐独立交付。

本片按一次明确的 **API 与展示契约修订**交付：包括 `stock_relations`、旧字段兼容语义、公司筛选顺序和关联理由详情，不可缩减为单独修复后端集合并集。理由详情用于防止多公司展示后把代表条理由误归给整组，不扩展为新的关联推断能力。

### 9.2 聚合与筛选顺序

1. 先按当前关注名单、请求时间窗口和来源类型取得候选。沿用现有 feed / pinned 各自的窗口，不为补全标签引入窗口外记录或未关注公司的记录。
2. 合并同一逻辑新闻的多公司关联，再按既有规则折叠媒体报道。两层合并都要保留关联集合；官方条目沿用逻辑公告合并，不参与媒体标题折叠。
3. 组级 `stock_codes` 为全部成员关联代码的并集，去重后稳定排序。代表条提供标题、摘要和主链接等原有代表字段，不决定组级关联范围。
4. `feed` 的 `stock` 筛选在聚合后执行：所选代码属于 `stock_codes` 就保留该组。对同一时间窗口和类型，选择 MU 或 WDC 时，同一组的公司集合、代表条及来源数保持一致。
5. 统计仍按组计新闻条数、按出版商去重计来源数。关联公司数量不增加新闻条数、来源数、热度或置顶权重。

`pinned` 复用同一组级关联聚合逻辑，保留其独立窗口、排序与上限；本片不增加置顶公司筛选。同一新闻在 feed 与 pinned 中因候选窗口不同而具有不同成员时，不承诺两者来源数或标签集合相同。

### 9.3 API 契约与关联理由

feed / pinned 中所有 `NewsEntry`（包括未折叠单条和官方条目）统一提供：

- `stock_codes: string[]`：本条或本组的关联关注股完整集合，去重、非空、按代码稳定排序。
- `stock_code: string`：保留兼容，取 `stock_codes[0]`；不代表主角、重要性排序或唯一关联公司。新页面以数组为准。
- `stock_relations: { stock_code: string; reasons: { text: string; source_id: number; source_record_id: string; url: string }[] }[]`：按公司列出可核对的已有理由及原记录出处；无可靠对应理由时返回空 `reasons`。公司顺序与 `stock_codes` 一致，同一公司相同理由和出处去重。

理由必须在丢弃原记录之前收集，不能仅从合并后的代表条复制。现有 `relation_reason` 存在新闻记录上，不天然等于每个关联公司的理由；只有能通过已有来源配置或记录证据确认归属时才放入该公司的 `reasons`。共享记录的理由归属不明时，保留公司关联而不生成理由，不根据标题推测，更不能解释为“共同利好/利空”。

原单数 `relation_reason` 保留兼容字段：单公司且只有一个明确理由时可返回该理由；多公司或含多个不同理由时返回 `null`。新页面从 `stock_relations` 展示公司对应的理由，不渲染一条未注明归属的组级理由。

前端 `NewsEntry` 类型同步补齐数组契约；`fold_count` 注释明确为去重出版商数，不能写成组内记录数。仅为新旧版本短暂兼容，数组字段缺失时可回退到单数代码；正常新接口必须返回数组，不能依赖前端回退掩盖后端缺失。

### 9.4 展示口径

采用同一关联公司组件，供普通信息流 `NewsRow`、置顶行 `PinnedRow`、详情 `NewsCard` 使用：

- 标签语义为「关联关注股」，不称为「受影响公司」。例如 `关联关注股：[MU] [WDC] · 3 个来源`。
- 普通信息流和置顶紧凑行最多展示 3 家，超出显示 `+N`，N 为尚未展示的公司数；点击后可展开全部并收起，键盘和触屏可操作，不仅依赖悬停。
- 详情完整展示全部公司，允许换行，不截断隐藏。关联理由在详情中按公司列出，并保留原记录链接；无理由时不生成解释文案。
- feed 当前筛选的公司优先展示，其余按代码稳定排序；置顶没有公司筛选上下文，按稳定代码顺序。展示排序不修改 API 的完整集合。
- 本片标签仅表达关联；不新增点击标签跳转、跨页导航或改变筛选的隐式行为。

这种紧凑展示可参考 [Benzinga Pro 官方手册](https://www.benzinga.com/pro/handbook-3) 的代码加 `+N` 形式；本产品采用点击展开以兼容触屏。多公司筛选可参考 [TradingView News Flow 筛选说明](https://www.tradingview.com/support/solutions/43000732560-news-flow-s-filters-overview/)。以上为交互参考，不表示照搬其新闻关联算法。

### 9.5 验收与交付

| 场景 | 必须满足的结果 |
| --- | --- |
| MU/WDC 同题、不同记录折叠 | 一组新闻同时返回两个代码；两层合并均不丢公司；重复关联不产生重复标签 |
| 切换 MU / WDC 公司筛选 | 同一窗口内均能命中该组，公司集合、来源数、代表条不因筛选改变；不相关公司筛选不能命中 |
| 代表条变化 | 改变发布时间使代表条切换，关联集合及已有理由出处仍完整，理由不串公司 |
| 同一逻辑新闻关联多家公司 | 只有一条逻辑记录也能显示多个标签；无法归属的新闻级理由不复制给每家公司 |
| 时间与类型边界 | 窗口外、未关注公司记录不混入；规范化标题不同或超出折叠边界时仍分别成组、不合并；未知时间仍独立；官方条目不与媒体误合并 |
| 来源和计数 | 同出版商经多个采集渠道、关联多家公司仍计一个来源；组级新闻计数不膨胀；不改变置顶入选和排名规则 |
| 三个显示位置 | 信息流、置顶、详情均展示数组；4 家以上的 `+N` 数量正确且可点击/键盘展开，详情完整换行；当前筛选公司可见 |
| 关联理由 | 不同公司各有出处，重复理由去重；无可靠理由只显示关联标签，旧单数字段不能泄漏为共同解释 |

## 10. 响应压缩修订（2026-10-27，已实施代码与隔离验证；真实链路验收待美股进程启用）

### 10.1 问题与本片边界

用户在国内前端 `/news` 观察到 feed 和 pinned 请求均耗时约 12 秒。已核对代码中的默认链路为：浏览器 → 国内 Vite `:5173` 的 `/api/us` 代理 → 美股后端 `:8000` → 数据库。实际部署可能有环境变量覆盖，启用前须核对运行配置，不能把这条链路直接当成 nginx 代理。

本轮只读采样：本机后端 feed 约 0.206 秒，返回 1,515,892 字节、874 条记录；pinned 约 0.062 秒、22,898 字节。客户端声明接受 gzip 后，后端仍返回未压缩 JSON。相同 feed 样本离线采用 gzip level 5 压缩为 399,539 字节，减少约 73.6%。这是固定样本的体积证据，不代表线上耗时保证，也不支持此前“必然压到 150 KB”的估计。

从美股机访问国内代理的样本未复现 12 秒；不能把这次采样当成用户浏览器的完整复现。feed 的大响应存在明确传输成本，但小体积 pinned 的 12 秒尚未被充分解释。本片验收应分别记录“压缩生效”和“用户慢请求是否改善”。

本片仅启用美股后端响应压缩，并验证代理透传。不改分页、新闻相关性、excerpt、折叠、SQL、缓存或页面业务行为，不把删减新闻作为性能修复；这些问题如需处理另行讨论。

### 10.2 实现合同

- 在 `config.py` 按现有 dataclass 配置方式新增 `STOCK_HTTP_GZIP_ENABLED`，默认 `false`；在 `web/app.py` 的应用工厂中按开关注册框架已有的 `GZipMiddleware`。压缩级别固定为 **5**，最小响应体 **1,024 字节**，不自写压缩算法。
- 本次仅在美股后端启用；国内后端保持默认关闭。开关是进程级配置，应用级中间件会影响该进程内其他符合条件的 HTTP 响应，不能声称只压缩 news 两个接口；验收须包含其他 API 的冒烟检查。
- 在响应离开美股服务器前完成压缩，才能减少跨境传输量。国内 Vite 优先沿用现有代理；先实测请求 `Accept-Encoding`、响应 `Content-Encoding` 和 `Vary` 是否正确通过，只有发现实际透传问题才补最小代理修复。不预设需要增加 nginx。
- 接受 gzip 的客户端获得 gzip 响应；明确只接受 identity 的客户端仍能正常读取。保留正确的 `Content-Type`、状态码、`Vary: Accept-Encoding` 及既有 CORS 行为，长度头必须与传输编码一致；已有编码的响应不得重复压缩。
- 浏览器使用原生解压，前端不增加手工解压逻辑，不改鉴权、请求参数、缓存政策或 API JSON 字段。新闻接口继续只查库，不引入采集或模型调用。
